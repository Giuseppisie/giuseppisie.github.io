16-bit MIPS-like CPU (Duke 250/16)

A Logisim single-cycle implementation of a 16-bit, word-addressed MIPS-like RISC CPU for teaching CPU design and architecture.

Role: Designer & implementer
Tools: Logisim (cpu.circ), assembler/simulator, RAM/ROM images

Project overview

Objective • Build a functional 16-bit MIPS-like RISC CPU in Logisim; single-cycle, word-addressed, Harvard-style memory.

This project implements the Duke 250/16 instruction set in a single-cycle Logisim CPU. It includes instruction fetch (ROM), data memory (RAM with the provided memory_latch wrapper), a tri-stated register file, an ALU that supports arithmetic/logical/shift ops, PC + next-PC logic, and I/O (TTY + keyboard). The design follows the course specification (instruction formats, clock/reset behavior, and memory layout). For the full assignment spec see the provided PDF. :contentReference[oaicite:0]{index=0}

Key features

  • R, I, and J instruction formats (4-bit opcode; 16-bit word-size)
  • Instruction support: addi, sub, add, not, and, sll, srl, lw, sw, bgez, beq, j, jr, jal, input, output.
  • 8 general-purpose registers ($r0..$r7; $r0 hardwired to 0; $r7 is link register).
  • Harvard architecture: separate ROM for instructions and RAM for data (use memory_latch with RAM in Logisim Evolution).
  • Clocking rules and reset behavior as required by the spec (register file and TTY on rising edge; PC, RAM, keyboard on falling edge; reset asynchronously clears PC/regs/TTY/keyboard).

Implementation notes

- The register file uses tri-state outputs + decoder (per spec recommendation).
- Data RAM is driven through the provided memory_latch circuit to work properly with Logisim Evolution's RAM timing model.
- Input instruction is non-blocking: returns ascii or 128 to indicate no data present (bits 15–8 zeroed; bit7 set to 1 when no data).
- Output writes low 7 bits to a 13×80 TTY (rising-edge triggered).

Quick reference

Word size: 16 bits (word-addressed)
Registers: 8 ($r0..$r7)
Memory: ROM (instr) + RAM (data w/ memory_latch)
Clocking: regfile & TTY rising-edge, PC & RAM & keyboard falling-edge
Reset: async reset must clear PC, registers, TTY, keyboard buffer (does not clear ROM/RAM content).

Memory model & testing

The assembler provided with the course generates ROM and RAM images. The memory layout reserves upper halves for kernel, with user instructions in 0x0000–0x7FFF and data/stack ranges as documented in the spec. Use the provided `hwtest.py` automated tester and the assembler/simulator to generate tests. The pdf includes detailed instructions on using the memory_latch with Logisim Evolution RAM — follow it exactly to avoid read/write timing problems. :contentReference[oaicite:2]{index=2}

Notes for the grader / demo

  • To boot: load ROM and RAM images into the Logisim components, ensure clock starts low, pulse reset, then step the clock.
  • Name the register file subcircuit RegisterFile and the reset input reset for the grader to detect probes.
  • Place probes named r0..r7 on each register so the autograder can read them.

Challenges, learnings & next steps

Building the single-cycle CPU forces you to reconcile instruction timing, edge-triggering constraints, and real RAM timing by using the memory_latch wrapper. The tri-state+decoder register file is a good exercise in physical-like design (avoids monolithic muxes). Next steps: add pipelining (stall/hazard handling), richer instruction set, or an interrupt/exception model.
